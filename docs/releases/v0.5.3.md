# depgraph v0.5.3

`v0.5.3`は、Windowsの公開後onboarding canaryを修正し、v0.5の互換性境界を維持するstable patch releaseである。
ソースにこの文書が存在するだけでは、公開完了を意味しない。
正式版には、署名付きannotated tagと[GitHub Release](https://github.com/TamaT-LLC/depgraph-cli/releases/tag/v0.5.3)が必要である。
`release-post-publish-evidence-v0.5.3.json`も、同じcommitと公開assetを指す必要がある。

## Windows公開後canaryの修正

`v0.5.2`のGitHub Releaseは、51点の公開assetと公開後証跡の生成・再取得検証まで完了した。
その後に追加されたWindowsのrepository-scoped MCP onboarding canaryは、Git Bash上の絶対パス`D:\...`をGNU tarへ渡した際、drive letterのコロンをremote archive separatorとして解釈されて停止した。
製品archive、checksum、MCP package smoke、compiler pack、公開後証跡の不一致ではない。

`v0.5.3`では、公開archiveの展開時にGNU tarの`--force-local`を指定する。
Linux、macOS、Windowsの5 targetで、公開archiveから`mcp setup`、再実行時のcache reuse、`status`、`update`、`uninstall`を確認する。
公開済み`v0.5.2`のtag、source、Release、asset、公開後証跡は置き換えない。

## リポジトリ単位のMCPセットアップ

Codexへのread-only MCP導入は、対象のGitリポジトリ内で次の1コマンドを実行すれば完了する。

```sh
depgraph mcp setup --host codex
```

このコマンドは、CLI versionとnative targetに一致する公式Release archive、compiler pack、checksum、公開後証跡を検証する。
検証済みruntimeはversionとtarget単位で共有し、Store、snapshot、Codex設定はリポジトリごとに分離する。
safe scanとMCP preflightが成功した後だけ、project-scopedな`.codex/config.toml`をatomicに更新する。
project codeの実行、mutation capability、shell expansion、ambient executable lookupは暗黙に有効化しない。

導入後の状態確認、再検証、削除には次のコマンドを使う。

```sh
depgraph mcp status --host codex
depgraph mcp update --host codex
depgraph mcp uninstall --host codex
```

## 互換性

`v0.5.3`は、`v0.5.2`と同じprotocol、Store、operation、MCP、release artifact契約を維持するpatch releaseである。

| Surface | `v0.5.3` contract |
| --- | --- |
| Product and Rust/Go/Web adapters | `0.5.3` |
| Previous stable release | `v0.5.2`, Store schema `17` |
| NDJSON worker protocol / graph schema | `1.0` |
| SQLite Store | schema `17` |
| Durable operation journal | schema `5` |
| MCP tool DTO | `depgraph-mcp-tools-v1` |
| Operation DTO | `depgraph-operation-v1` |
| Agent host configuration | `depgraph-agent-host-config-v1` |
| Agent onboarding release evidence | `release-post-publish-evidence-v1` |
| Packaged MCP smoke | `mcp-package-smoke-v2` |
| Native package smoke | `stable-v0.5.0-packaged-smoke-v1` |
| Stable release gate | `stable-release-gate-v2` |

Store schema、operation journal schema、worker protocol、MCP DTO、既存CLIの既定値に変更はない。
`v0.5.2`のStoreはmigrationなしで開ける。
異なるversionのbinary、worker、compiler pack、manifest、Storeを一つの実行環境で混在させない。

古いStoreに対する検証は、公式`v0.4.0-rc.6` schema-13 fixtureからschema 17へのtransactional migrationを維持する。
対象は`xtask/fixtures/v0.4.0-rc.6-store-v13.sql`であり、SHA-256は`43fe0dda73d03be9b8fff2ed9ff8ce888ad96e41e78335a1117646475c937150`である。
rollback時はwriterを停止し、移行済みdatabaseを退避する。
その後、事前に保存したdatabaseとWAL/SHM一式を復元する。

## 配布対象

GitHub Releaseとnpmは、同じrelease closureから5つのnative targetを提供する。

| OS | Architecture | Native target |
| --- | --- | --- |
| Linux | x86-64 | `x86_64-unknown-linux-gnu` |
| Linux | ARM64 | `aarch64-unknown-linux-gnu` |
| macOS | Intel | `x86_64-apple-darwin` |
| macOS | Apple Silicon | `aarch64-apple-darwin` |
| Windows | x86-64 | `x86_64-pc-windows-msvc` |

npmでは`@tamat-llc/depgraph`と5つのnative packageを公開する。
Windows packageは`@tamat-llc/depgraph-win32-x64`である。
公開にはnpm Trusted Publishingを使用し、native packageを先に、root packageを最後に公開する。
npm launcherにはNode.js 24以上が必要であり、Linuxはglibc targetのみを対象とする。
musl環境はこのreleaseの対象外である。

## Release sourceと公開条件

`v0.5.3`のstable baseline statusは`maintenance-ref-pinned`である。
remote `main`、`refs/heads/release/0.5`、署名付きtagは、公開開始時に同じreview済みcommitを指す必要がある。
そのexact commitで8 jobの手動Full CIを完走する。
release workflowは、5 targetのarchiveとcompiler packを再構築する。
公開後はGitHub Releaseから全assetを再取得し、workflow artifactとのbyte一致、公開Linux canary、5 targetのrepository-scoped MCP onboardingを検証する。

GitHub Releaseと`release-post-publish-evidence-v0.5.3.json`が揃い、Release workflowが成功した後に、npm workflowを`v0.5.3` tagへdispatchする。
`v0.5.2`以前のtag、Release、asset、公開後証跡は変更しない。

## 既知の制約

`mcp setup`は現在Codexのproject-scoped設定だけを変更する。
CLI versionと完全一致する公開済みstable releaseがない場合、nightlyやlocal artifactへfallbackしない。
Safe scanは対象repositoryのbuild script、plugin、package managerを実行しない。
Compiler-precise modeとframework build observationは、明示的な同意と一致するcompiler packを要求する。
製品サポートはベストエフォートであり、応答時間や解決時間のSLAは設けない。
