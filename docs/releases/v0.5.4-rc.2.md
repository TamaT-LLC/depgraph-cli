# depgraph v0.5.4-rc.2

`v0.5.4-rc.2` は、インストール後の実行経路を修正した評価用の release candidate である。
`v0.5.4-rc.1` で追加した code-health と Agent dogfood v2 の契約は変更しない。
既存の stable `v0.5.4` と、その Store schema `17` の互換性契約も変更しない。

`v0.5.4-rc.1` は、配布物の外にあるバージョン付きシンボリックリンクから起動すると、
配布物内の Rust／Go／Web worker を検出できなかった。
インストーラーが作る通常の実行経路で `doctor` と scan が失敗するため、
この問題を修正した成果物は新しい RC 番号で公開する。
公開済みの RC1 tag と asset は移動も置換もしない。

## RC2 で修正したこと

実行ファイルの実体を基準に配布物のルートを解決するようにした。
配布物の外にあるバージョン付きシンボリックリンクから起動しても、
checksum で確認済みの worker と Web runtime を選択できる。
配布物ルート自体がシンボリックリンクの場合は、従来どおり安全側に失敗する。

配布 archive を単体で再検証するコマンドも追加した。

```bash
cargo xtask verify-release-archive \
  --archive /absolute/path/to/depgraph-0.5.4-TARGET_TRIPLE.tar.gz
```

checksum sidecar を省略した場合は、archive と同じ場所の `<archive>.sha256` を使う。
対象は実行ホストと同じ target、かつ workspace と同じ product version に限る。
検証では manifest と全必須 artifact、`doctor`、Web／Rust／Go scan、query、export、
MCP onboarding を実行する。バージョン付きシンボリックリンク経由の起動も含む。

archive の展開とハッシュ計算は、入力サイズと展開量に上限を設けた streaming 処理にした。
不正な path、重複 entry、symlink、特殊 file、過大な metadata を公開前に拒否する。
検証用 directory は成功時と失敗時の両方で削除する。
冷えた環境での packaged MCP 起動に合わせ、initialize の期限は30秒とする。

## Compatibility tuple

互換性 tuple は RC1 から変更しない。

| Surface | `v0.5.4-rc.2` contract |
| --- | --- |
| Product and Rust/Go/Web adapters | `0.5.4` (evaluation RC only) |
| Stable baseline (immutable) | `v0.5.4`, Store schema `17` |
| NDJSON worker protocol / graph schema | `1.0` |
| SQLite Store | schema `18` (post-tag `main` evaluation contract) |
| Durable operation journal | schema `5` |
| Health analyzer | `1.0.3` |
| MCP tool DTO | `depgraph-mcp-tools-v1` |
| Operation DTO | `depgraph-operation-v1` |
| Packaged MCP smoke | `mcp-package-smoke-v3` |
| Agent dogfood corpus | `agent-dogfood-spec-v2` |
| Stable release gate | `stable-release-gate-v2` |
| Snapshot seal | provenance-aware seal `v2` (legacy seal `v1` verified during migration) |
| Post-publish evidence | `release-post-publish-evidence-v1` |

worker protocol、operation journal、既存 CLI の既定値は RC1 と同じである。
候補の Store は schema `18` を使用する。
異なる version の binary、worker、compiler pack、manifest、Store を混在させない。

## Store migration and rollback

Store の移行と rollback 手順は RC1 から変更しない。
schema `17` から schema `18` への移行は一つの transaction で完結する。
失敗時は全体を rollback し、部分的な Store を公開しない。

移行前に daemon、MCP server、operation runner と全 Store writer を停止する。
すべての SQLite connection を閉じてから、database と WAL／SHM を一組で保存する。
schema `18` へ移行した database を stable `v0.5.4` 以前の binary で開いてはならない。
rollback では schema-18 database を退避し、保存した一式を復元してから旧 binary を起動する。
詳細は [Agent host operations runbook](../50_test/mcp-agent-host-operations.md#upgrade-and-rollback-policy) に従う。

## Release closure

RC2 は、手動 Full CI が成功した `main` の exact commit からだけ公開する。
同じ commit を指す署名付き annotated tag `v0.5.4-rc.2` が必要である。
Release workflow は5 targetの通常 archive と compiler pack を再構築し、
checksum、manifest、SBOM、license、package smoke、compiler handshake、
stable gate を検証してから prerelease を公開する。

公開後は GitHub Release から全 asset を再取得し、workflow artifact と byte 一致することを確認する。
`release-post-publish-evidence-v0.5.4-rc.2.json` は candidate commit、tag object、
Full CI、Release run、全 asset digest と aggregate report を同じ候補へ固定する。

## Known constraints

- RC2 は評価用であり、stable support SLA を持たない。
- Safe scan は project code、build script、plugin、package manager を実行しない。
- Compiler-precise mode と framework build observation は、明示的な同意と一致する compiler pack を要求する。
- 単体 archive の完全な検証には30分以上かかる場合がある。
- `verify-release-archive` は通常 archive を検証する。tag、公開後 evidence、compiler pack は Release workflow が別に検証する。
- Agent dogfood v2 の実 evidence と digest pin は、RC2 の公開 closure が完成した後に別の review 済み PR で固定する。
