# depgraph v0.5.0-rc.1

This is the first v0.5 release candidate and the first published candidate that
contains the native MCP stdio server and durable operation runtime. It is an
evaluation release, not a supported stable release. The stable `v0.5.0` source
remains blocked until the GA task pins an independently reviewed exact
full-CI-green baseline.

## Included scope

- Native `depgraph`, `depgraph-mcp`, and `depgraph-operation-runner` binaries
  for Linux x86-64/ARM64, macOS Intel/Apple Silicon, and Windows x86-64.
- Rust, Go, and Web dependency graph adapters using worker protocol `1.0`.
- Fixed-root MCP read/query tools, safe scan and runtime import, confined
  repository writes, daemon control, and explicitly authorized project-build
  operations.
- Durable idempotent operation submission, polling, cancellation, reconnect,
  deadline handling, retention, and tombstones.
- Confined Windows repository writes keep private staging files exclusive
  until handle-relative publication. Cleanup uses POSIX disposition when
  available and sanitizes content before the legacy delete-pending fallback.
- Five target-native normal archives and five compiler packs with checksums,
  manifests, SBOMs, license inventories, schemas, native smoke reports, and
  aggregate verification reports.

compatibility surfaces. A matching product version does not permit a host to
ignore a tuple mismatch.

## Agent host configuration

Verify the archive checksum and `release-manifest.json`, extract the matching
target archive, and configure the host with canonical absolute paths. This
read-only profile is the default:

```json
{
  "mcpServers": {
    "depgraph": {
      "command": "/absolute/path/to/depgraph-0.5.0-TARGET_TRIPLE/bin/depgraph-mcp",
      "args": [
        "--root", "/absolute/path/to/repository",
        "--store", "/absolute/path/to/state/depgraph.sqlite",
        "--capability", "read",
        "--compiler-pack-requirement", "/absolute/path/to/compiler-pack-requirement.json",
        "--log-level", "warn"
      ]
    }
  }
}
```

The server seals `--root` for its lifetime. Keep the Store and sibling
`<store>.operations.sqlite` journal private to that root and host account.
Use the complete replacement profiles in the
[Agent host operations runbook](../50_test/mcp-agent-host-operations.md) when
`store-write`, `repository-write`, `daemon-control`, or `project-exec` is
required. `project-exec` additionally requires an independent human decision,
`acknowledgement: true`, and a verified target compiler-pack requirement.

## Upgrade and rollback

The canonical migration input is the checksum-pinned official
`v0.4.0-rc.6` Store schema-13 fixture. v0.5 transactionally migrates it to
Store schema 17 while preserving the completed graph identity, integrity, and
query behavior.

1. Stop the daemon, MCP server, operation runner, and every Store writer.
2. Close SQLite and copy the database with its matching WAL/SHM files as one
   backup set; record each checksum.
3. Open the original with v0.5 and verify schema 17, snapshot identity,
   integrity, and required queries before resuming writers.
4. Keep the byte-identical pre-upgrade backup for the rollback window.

Downgrade-in-place is unsupported. To roll back, stop v0.5, preserve the
schema-17 database separately, restore the complete checksum-matching backup,
and only then start the prior binary. The operation journal is a separate
schema-5 database and must not be substituted for a Store backup.

## Known constraints

- MCP is experimental in this candidate and is not a remote multi-tenant
  service. The supported transport is a host-launched stdio process.
- Release candidates are best-effort evaluation builds without a stable-line
  support SLA. No `v0.4.0` stable GitHub Release was published.
- Safe scans do not execute project code. Compiler-precise resolution is
  opt-in, target-bound, and fails closed without its verified compiler pack.
- Durable work survives stdio disconnects, but the reconnecting host must use
  the same root, Store, capability profile, and compiler-pack requirement.
- Tasks clients negotiate revision `2026-07-28`; legacy clients use the
  portable operation handle and polling tools for the same journal record.
- Linux x86-64 Full CI and release package builds opt out of Rust 1.93's
  self-contained `rust-lld` and use the hosted runner's system linker. Repeated
  large debug relinks crash the pinned `rust-lld` with `SIGBUS`; this changes
  only the build linker, not the archive's runtime or compatibility tuple.
- Pushed tags and published assets are immutable. Any source correction uses a
  new RC number; `v0.5.0-rc.1` is never moved or republished.

## Release closure and evidence

The candidate is created only from a signed annotated `v0.5.0-rc.1` tag whose
peeled commit equals the exact successful manual `workflow_dispatch` CI head.
That full CI run must complete Rust, Go, Web, compiler-precise hostile,
benchmark, Linux/macOS integration, and Windows smoke jobs without a skip or
failure.

Benchmark report v7 records the 500 ms impact and 2 second incremental product
targets separately from bounded GitHub-hosted-runner regression ceilings. Its
repeated impact samples use independent immutable Store reads and canonical
recomputation; the report rejects the obsolete impact-query-cache condition so
the release gate matches the Agent read-only contract.

The tag-triggered Release workflow rebuilds all assets, runs the five-target
normal archive and compiler-pack aggregate gates, and publishes only after
`stable-release-gate-v2` allows the candidate. Its final job then downloads the
public GitHub Release assets again, reruns checksum, manifest, SBOM, license,
schema, packaged MCP, operation, and compiler handshake verification, and
requires every public byte to match the corresponding workflow artifact.

`release-post-publish-evidence-v0.5.0-rc.1.json` records the candidate commit
and tree, signed tag object and verification result, full CI run and all eight
job results, Release run, all 51 pre-evidence asset sizes and SHA-256 digests,
aggregate report digests, and the canonical asset-set digest. The workflow
uploads that JSON to the same prerelease and downloads it once more to prove
the published evidence bytes match. Verification uses only the public release
archives and sidecars; it does not substitute checkout-built product binaries
or unpublished package artifacts.
