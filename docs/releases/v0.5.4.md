# depgraph v0.5.4

`v0.5.4`は、Codex、Claude Code、Cursor、Grokにscoped MCP setupを追加するstable patch releaseである。
ソースにこの文書が存在するだけでは、公開完了を意味しない。
正式版には、署名付きannotated tagと[GitHub Release](https://github.com/TamaT-LLC/depgraph-cli/releases/tag/v0.5.4)が必要である。
`release-post-publish-evidence-v0.5.4.json`も、同じcommitと公開assetを指す必要がある。

## 4つのAgent hostへのMCPセットアップ

`mcp setup`、`status`、`update`、`uninstall`は、Codex、Claude Code、Cursor、Grokに対応する。
対象のGitリポジトリ内で、ホストとscopeを指定して実行する。

```sh
depgraph mcp setup --host codex
depgraph mcp setup --host cursor --scope user
```

project scopeが既定であり、サーバー名は従来どおり`depgraph`となる。
user scopeでは`depgraph-<repository-id>`を使い、複数リポジトリの設定を共存させる。
設定先は次のとおりである。

| Host | Project scope | User scope |
| --- | --- | --- |
| Codex | `.codex/config.toml` | `~/.codex/config.toml` |
| Claude Code | `.mcp.json` | `~/.claude.json` |
| Cursor | `.cursor/mcp.json` | `~/.cursor/mcp.json` |
| Grok | `.grok/config.toml` | `~/.grok/config.toml` |

既存の無関係な設定は保持する。
CodexとGrokのTOMLではコメントと書式も保持する。
user scopeの設定変更はファイル単位のlockで直列化し、異なるリポジトリからの同時更新による上書きを防ぐ。

## ライフサイクルと所有権

各bindingは、canonical repository root、CLI version、native target、Store、compiler pack、read-only capabilityを固定する。
`status`は公開asset、Store、snapshot、host設定、MCP接続を再検証する。
`update`は実行中CLIのversionに合わせてartifactとsafe snapshotを更新する。

`uninstall`は指定したhost／scopeの所有済みentryだけを削除する。
同じrepository、version、targetを指す別の所有済みbindingが残る間はrepository stateを保持する。
最後のbindingを削除した時点で専用stateを削除し、共有済みの検証済みartifactは残す。
過去releaseや同名の無関係なentryは、stateを保持するbindingとして扱わない。

## 互換性

公開済み`v0.5.4`は、`v0.5.3`のprotocol、operation、MCP、Store、release artifact契約を維持するpatch releaseである。

| Surface | `v0.5.4` contract |
| --- | --- |
| Product and Rust/Go/Web adapters | `0.5.4` |
| Previous stable release | `v0.5.3`, Store schema `17` |
| NDJSON worker protocol / graph schema | `1.0` |
| SQLite Store | schema `17` |
| Durable operation journal | schema `5` |
| MCP tool DTO | `depgraph-mcp-tools-v1` |
| Operation DTO | `depgraph-operation-v1` |
| Agent host configuration | `depgraph-agent-host-config-v1` |
| Agent onboarding release evidence | `release-post-publish-evidence-v1` |
| Packaged MCP smoke | `mcp-package-smoke-v2` |
| Native package smoke | `stable-v0.5.0-packaged-smoke-v1` |
| Stable release gate | `stable-release-gate-v2` |

operation journal schema、worker protocol、MCP DTO、Store schema、既存CLIの既定値に変更はない。
`v0.5.3`と`v0.5.4`のStoreはいずれもschema 17であり、このstable patchはStore migrationを行わない。
異なるversionのbinary、worker、compiler pack、manifest、Storeを一つの実行環境で混在させない。

この互換性宣言は、署名付き`v0.5.4` tagとその公開artifactに適用される。
tag後の`main`開発線に自動的に遡及しない。

## 公開tagとmain開発線の境界

履歴上、直近の公開tag `v0.5.3`（peeled commit
`ebac6e8836905164d5e1522f7c87844d5d8e2fe7`）と`v0.5.4`（peeled commit
`ea16edec63e88923c7d169152caedbf4285b4713`）には、code-health の
`depgraph-core/src/health/hotspot.rs`、`HealthFinding`、または
`AgentHealthFinding` の hotspot score field は存在しない。
最初の code-health API は、`v0.5.4` tag より後の Issue #423 実装 commit
`e21040064d44bce34088ff5e8eddecf784c12516` で導入され、Issue #440 はその
後の開発線で拡張した。

tag後の現行`main`／評価用RCは、Store schema 18、health provenance 3項目、
provenance-aware seal v2、health analyzer `1.0.2`、finding contract
`depgraph-health-finding-v1`、`hotspot_scores`、およびpackaged MCP smoke
`mcp-package-smoke-v3`を使う。
このtupleは公開済み`v0.5.4` artifactの契約ではない。
schema 17のStoreを18へtransactional migrationし、検証済みseal v1をseal v2へ
再構築する未公開の開発契約である。

したがって、#440 の`score_hotspots` return type、`HotspotAnalysisError`、
`HealthFinding.hotspot_scores`、および`depgraph-mcp-tools-v1` の新しい
closed DTO field は、公開済み`v0.5.3`／`v0.5.4` artifactのAPIを壊す変更では
ない。一方、#423／#440 を含む現在の`main`は公開済み`v0.5.4`とは別の未公開
開発線である。`score_hotspots`を`Vec<HealthFinding>`から`Result<...>`へ
変更したため、#423 の未公開開発版を利用していたRust callerにはmigrationが
必要であり、`HotspotAnalysisError::InvalidInput`追加とpublic struct field追加も
source compatibilityに影響する。

Issue `#423` の開発版callerをこの契約へ移行する場合は、`score_hotspots(...)?`のように
`Result`を処理し、`HotspotAnalysisError`の`InvalidInput`／cancel／resourceを
呼び出し側の終了・再試行方針へ明示的に写像する。`HealthFinding`を直接構築する
callerは`hotspot_scores`を設定し、hotspotをAgent DTOへ投影するcallerは新しい
5層score objectを必須出力する。過去wire入力のmissing／null score受理は、この
新規出力要件を緩めるものではない。

この変更を次に公開する際は、v0.5 stable patchとして黙って出荷せず、公開OSS
release governanceに従った新しいminor versionとmigration contract（または
明示した新しいcontract version）を選定する。既存のv0.5.4利用者が受け取る
artifactと、tag後`main`の開発APIを混在させてはならない。

なお、#436の`v0.5.4-rc.1`のようにtag後に作成するcandidateは、既存のstable
`v0.5.4`を置換しない評価専用であり、stable利用者へ配布しない。candidateで
新しいRust／MCP契約を検証できても、次のstable公開は新しいminor versionと
contract migrationの判定後に行う。

公開済みstable artifactの互換性検証は、公式`v0.4.0-rc.6` schema-13 fixtureからschema 17へのtransactional migrationを維持する。
tag後の現行`main`は、同じfixtureをschema 18までmigrationし、schema 17から18への段階でlegacy seal v1を検証してprovenance-aware seal v2へ再構築する。
対象は`xtask/fixtures/v0.4.0-rc.6-store-v13.sql`であり、SHA-256は`43fe0dda73d03be9b8fff2ed9ff8ce888ad96e41e78335a1117646475c937150`である。
rollback時はwriterを停止し、移行済みdatabaseを退避する。
その後、事前に保存したdatabaseとWAL/SHM一式を復元する。

## 配布対象

GitHub Releaseとnpmは、同じrelease closureから5つのnative targetを提供する。

| OS | Architecture | Native target |
| --- | --- | --- |
| Linux | x86-64 | `x86_64-unknown-linux-gnu` |
| Linux | ARM64 | `aarch64-unknown-linux-gnu` |
| macOS | Intel | `x86_64-apple-darwin` |
| macOS | Apple Silicon | `aarch64-apple-darwin` |
| Windows | x86-64 | `x86_64-pc-windows-msvc` |

npmでは`@tamat-llc/depgraph`と5つのnative packageを公開する。
Windows packageは`@tamat-llc/depgraph-win32-x64`である。
公開にはnpm Trusted Publishingを使用し、native packageを先に、root packageを最後に公開する。
npm launcherにはNode.js 24以上が必要であり、Linuxはglibc targetのみを対象とする。
musl環境はこのreleaseの対象外である。

## Release sourceと公開条件

`v0.5.4`のstable baseline statusは`maintenance-ref-pinned`である。
remote `main`、`refs/heads/release/0.5`、署名付きtagは、公開開始時に同じreview済みcommitを指す必要がある。
そのexact commitで8 jobの手動Full CIを完走する。
release workflowは、5 targetのarchiveとcompiler packを再構築する。
公開後はGitHub Releaseから全assetを再取得し、workflow artifactとのbyte一致と公開Linux canaryを検証する。
5 targetでは、4ホストのproject scopeとuser scopeについてsetup、status、update、uninstallを確認する。

GitHub Releaseと`release-post-publish-evidence-v0.5.4.json`が揃い、Release workflowが成功した後に、npm workflowを`v0.5.4` tagへdispatchする。
`v0.5.3`以前のtag、Release、asset、公開後証跡は変更しない。

## 既知の制約

CLI versionと完全一致する公開済みstable releaseがない場合、nightlyやlocal artifactへfallbackしない。
Safe scanは対象repositoryのbuild script、plugin、package managerを実行しない。
Claude Codeのproject scopeは、host側でリポジトリ設定へのtrust承認を必要とする。
Compiler-precise modeとframework build observationは、明示的な同意と一致するcompiler packを要求する。
製品サポートはベストエフォートであり、応答時間や解決時間のSLAは設けない。
