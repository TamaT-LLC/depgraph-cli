# depgraph v0.4.0

This is the first stable Milestone 4 release. It promotes the compatibility
candidate `v0.4.0-rc.1` after closing the release contract for immutable
snapshots, diff and impact, incremental analysis, architecture policy, runtime
evidence, GraphML, framework Build Evidence, and the Rust HIR/sysroot backend.

## Stable compatibility promise

| Component | Stable v0.4.0 contract |
| --- | --- |
| Product and Rust/Go/Web adapters | `0.4.0` |
| Stable upgrade source | `v0.4.0-rc.1`, store schema `11` |
| NDJSON protocol and graph schema | `1.0` |
| SQLite store schema | `13` |
| Minimum migratable store schema | `1` |
| Independently tested legacy store | `v0.2.0-rc.1`, schema `5` |
| Syntax/semantic/build and impact-query cache | contract `1` |
| Snapshot diff / policy / runtime trace / GraphML | `1.0` |
| Incremental plan / daemon status | `incremental-plan-v1` / `daemon-status-v1` |
| Framework build graph / release gate | `framework-build-graph-v1` / `dynamic-framework-evidence-release-gate-v1` |
| Runtime collector | `runtime-collector-v1` |
| Native package smoke | `stable-v0.4.0-packaged-smoke-v1` |
| Stable release gate | `stable-release-gate-v1` |

For the `0.4.x` line, existing commands, option meanings, exit-status
categories, JSON envelope fields, protocol `1.0`, and store data remain
compatible. Patch releases may add optional fields, commands, adapters,
diagnostics, or conservative analysis results. They must not remove or
reinterpret an existing field, silently promote uncertain evidence to exact,
or make a schema-13 store unreadable. A breaking CLI, protocol, graph, or store
change requires a new minor release and an explicit migration contract.

Cache entries are derived data. A patch may invalidate and rebuild them when
the contract or analyzer input changes; invalidation must not alter completed
snapshots. Stores newer than schema `13`, unknown protocol events, unknown
manifest compatibility fields, and modified release artifacts fail closed.

## Release baseline and maintenance line

The stable line is anchored by `release-baseline-v1`:

| Field | Exact value |
| --- | --- |
| Repository | `TamaT-LLC/depgraph-cli` |
| Release | `0.4.0` |
| Baseline commit | `d5ca92bae4b4fdbbedb2f3cabd4aa3ef731e7c9f` |
| Baseline tree | `46555a059070e94c3ed4567af3c58b278dbb0fb4` |
| Maintenance branch | `refs/heads/release/0.4` |
| Canonical baseline digest | `sha256:0bb7f33d212402025429382489d586956d16f7d63d2e4d9d781d5715a44b00fd` |

The digest is SHA-256 over these UTF-8 bytes, including the final newline:

```text
release-baseline-v1
repository=TamaT-LLC/depgraph-cli
version=0.4.0
commit=d5ca92bae4b4fdbbedb2f3cabd4aa3ef731e7c9f
```

An operator reproduces the anchor after fetching it:

```bash
git fetch origin refs/heads/release/0.4
test "$(git rev-parse FETCH_HEAD^{commit})" = d5ca92bae4b4fdbbedb2f3cabd4aa3ef731e7c9f
test "$(git rev-parse FETCH_HEAD^{tree})" = 46555a059070e94c3ed4567af3c58b278dbb0fb4
printf '%s\n' \
  release-baseline-v1 \
  repository=TamaT-LLC/depgraph-cli \
  version=0.4.0 \
  commit=d5ca92bae4b4fdbbedb2f3cabd4aa3ef731e7c9f |
  shasum -a 256
```

The initial `release/0.4` ref points at the exact baseline. It is not a second
development branch and must not receive a wholesale merge from `main`.
Maintenance changes use one of these observable flows:

1. A fix needed on both lines lands on `main` through a green, reviewed pull
   request. A separate pull request targeting `release/0.4` cherry-picks the
   reviewed commit with `git cherry-pick -x`; its body records the main commit,
   issue, compatibility impact, and 0.4.x verification.
2. An urgent 0.4.x-only fix starts from `release/0.4`, lands there through a
   green, reviewed pull request, and is then forward-ported to `main` in a
   separate pull request. The forward-port records the stable commit.
3. A change that cannot preserve this document's 0.4.x compatibility promise
   is rejected from `release/0.4`. It remains a next-minor change on `main`.

The maintenance ref advances only through those pull requests. Force-pushes
and history rewrites are forbidden. Each patch release records its candidate
commit and gate/artifact digests; the baseline above remains the ancestry
anchor even after approved patch commits advance the branch.

`v0.4.0` is a one-time immutable tag whose peeled commit must equal the
baseline commit. Before pushing the tag, the release operator fetches the
remote maintenance ref, verifies the commit, tree, and canonical digest above,
runs the full release checklist, and creates a signed annotated tag directly
on that commit. A tag on any other commit is invalid.

The baseline predates this contract and cannot contain a new self-check
without changing its immutable commit. The `Stable release source guard`
therefore runs from the default branch on the `requested` event for every
`Release` workflow. For `v0.4.0`, it compares the requested run's `head_sha`
with the baseline before the baseline workflow can finish. A mismatch cancels
the release run and deletes the invalid tag, so its `publish` job cannot find
the verified remote tag. This source-independent guard is the enforcement
boundary; the baseline's existing `stable-release-gate-v1` remains the
artifact, compatibility, benchmark, and job-closure boundary.

`main` is the next-version development line. New behavior added there while
0.4.x is supported must be default-disabled or explicitly opt-in whenever it
could change existing CLI output, exit status, protocol/store interpretation,
analysis completeness, resource use, or project-code execution. Enabling a
breaking default requires a new minor release, an explicit migration contract,
and updated release gates; it is never backported as a 0.4.x patch.

## Machine-readable stable gate

The tag workflow emits `stable-release-gate.json`. Its closed schema is
`stable-release-gate-v1`, its decision is exactly `allow` or `reject`, and it
binds the SHA-256 digests of `release-verification.json` and
`benchmark-report.json`. It also records the tag context, workflow source SHA,
and four direct GitHub Actions job results rather than assuming that local
execution proves CI success. The gate allows `v0.4.0` only when every check
passes:

1. The workspace, tag, archives, workers, manifests, and report identify
   stable `0.4.0`.
2. Protocol/graph `1.0`, store `13`, cache `1`, and every compiled
   compatibility field match exactly.
3. The official `v0.4.0-rc.1` schema-11 fixture passes the upgrade and rollback
   checks.
4. All five native package closures and their licenses/attestations pass.
5. The exact 10,000-file benchmark report passes all seven gated metrics.
6. Framework Build Evidence and runtime collector contracts match the compiled
   ledgers.
7. GitHub Actions has completed `quality`, `benchmark`, `package`, and
   `verify-assets`; these are direct dependencies of `stable-gate`.
8. The default-branch source guard has allowed only a workflow request whose
   tag and source SHA match the immutable `release-baseline-v1` commit.

The command writes a `reject` report and exits non-zero if a criterion drifts.
The `publish` job depends on `stable-gate`, so it cannot publish rejected
evidence.

## GA exit criteria

| Area | Required evidence |
| --- | --- |
| Quality | `cargo xtask test`, formatting, Clippy, Rust/Go/Web tests, race tests, and semantic E2E are green |
| Performance | `depgraph-benchmark-report-v4`, exact deterministic fixture, conservation checks, and all gated metrics pass |
| Migration | RC.1 schema-13 and legacy schema-5 fixtures retain completed graph integrity and immutable identity |
| Safety | Safe scan executes no project code; tamper, symlink, unknown contract, and unsupported schema paths fail closed |
| Packages | Linux x64/arm64, macOS x64/arm64, and Windows x64 archives pass native smoke and aggregate closure |
| Frameworks | Next.js, Astro, TanStack Router, and TanStack Start capability ledger and build-union E2E pass |
| Collector | `runtime-collector-v1` is checksum-attested and its real fixture trace validates, imports, and queries |
| Supply chain | Checksums, manifests, SPDX SBOM, project licenses, third-party notices, worker/backend/sysroot attestations pass |

The benchmark product targets are 30 seconds for a fresh initial scan, 2
seconds for one-file incremental work, and 500 milliseconds for a warm impact
query. Hosted-runner release ceilings remain 80 seconds, 2 seconds, and 500
milliseconds respectively. The report allows one bounded outlier with a 20%
hard noise allowance and retains every raw sample.

## Upgrade and migration

The repository contains an SQL fixture produced by the official
`v0.4.0-rc.1` packaged binary at its exact schema `11`. Unit tests and every
packaged archive:

- migrate the schema-11 store transactionally to schema `13` with the stable
  binary;
- retain its completed scan, two nodes, one dependency site, one edge, two
  evidence records, coverage, and verified immutable graph identity;
- create and resolve a snapshot name without changing that identity; and
- leave a byte-separated rollback copy at schema `11`.

The existing official `v0.2.0-rc.1` schema-5 fixture is also migrated
transactionally to schema `13` and checked through snapshot, export, and `why`
queries.

Before upgrade, stop the daemon and close SQLite cleanly. Copy the database and
any `-wal`/`-shm` files as one backup set. Opening schema `1` through `12`
performs an in-place transactional migration. Downgrade-in-place is not
supported.

## Rollback

1. Stop the stable daemon and all writers.
2. Preserve the upgraded database separately for diagnosis.
3. Restore the complete pre-upgrade database backup and matching WAL/SHM files.
4. Restart the previous binary that created that backup.

Do not copy individual tables between schema versions. If release publication
itself fails, do not replace the tag or reuse partial artifacts: remove the
failed release entry, fix on a new commit, and create a new version/tag.

## Known limitations

- Dynamic language behavior, reflection, native callbacks, proc-macro output,
  open dispatch, and unobserved build/runtime paths remain explicit
  candidate/external/unresolved boundaries.
- Safe scans do not execute project config, plugins, package managers,
  generators, build scripts, proc macros, or local compiler binaries.
- Build observation requires `--allow-project-code` and is a separately
  supervised privileged operation.
- Runtime evidence depends on an explicitly deployed reference collector; a
  safe scan does not observe production traffic.
- Architecture policy can evaluate only evidence in the selected completed
  snapshots.
- One-file Web changes use the sparse incremental path only when its exact
  closure can be proven; other changes fall back atomically to a full scan.
- Third-party GraphML viewers may ignore depgraph's canonical JSON data keys.
- Windows on ARM and Linux distributions without the packaged archive's
  runtime ABI are not in the GA package matrix.

Every patch release must review this list. A newly discovered limitation is
added before publishing the fix or mitigation; an item is removed only when a
regression test and the relevant compatibility/package gate prove closure.
Security or data-integrity limitations are never deferred to an undocumented
follow-up. Support-matrix changes are called out in the release note and cannot
silently narrow an existing `0.4.x` guarantee.

## Release checklist

- [ ] Version and worker handshakes are synchronized.
- [ ] Compatibility contract and RC.1/legacy fixtures pass.
- [ ] `cargo xtask test` is green on the pinned toolchains.
- [ ] Benchmark report is exact and green.
- [ ] All five package jobs and aggregate asset verification are green.
- [ ] `stable-release-gate.json` says `allow` and binds both input digests.
- [ ] `release/0.4`, the baseline digest, and the peeled `v0.4.0` tag source
      match the exact baseline commit.
- [ ] GitHub Actions and Greptile have no unresolved failure or finding.
- [ ] Release note, support matrix, rollback, and known limitations are current.
- [ ] The immutable tag points at the reviewed merge commit.

The published release includes all five archives and SHA-256 sidecars,
`release-verification.json`, `benchmark-report.json`, and
`stable-release-gate.json`. Each archive includes the core, Rust/Go/Web
workers, protocol schema, required Web runtime components, bundled Rust
standard-library source tree, release manifest, SPDX SBOM, both project
licenses, and third-party notices.
